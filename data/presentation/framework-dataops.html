¿Qué cubre el framework? Automatizar el paso de artefactos de datos desde un repositorio Git hacia los ambientes dev, qa y prd en GCP — sin scripts manuales ni procedimientos ad-hoc.

¿Qué queremos lograr?

Sincronizar los equipos de Desarrollo y Operación en despliegues a producción, a través de 3 pilares.

🗄️
Repositorios

Versionamiento y control de código como fuente de verdad de todo despliegue

⚙️
CI/CD Engine

Despliegue automatizado con Cloud Build — sin intervención manual en prd

🤝
Equipos Sincronizados

Dev y Ops trabajan sobre el mismo artefacto ya validado en ambientes previos

Requisitos

Lo necesario para adoptar el Framework DataOps

Requisitos del Framework

🗄️ Repositorio

Servicio de versionamiento de código:

  • GitLab / GitHub / Azure Repos
  • Manejo básico de Git
  • Rama de certificación (dev) y producción (prd)
⚙️ Configuración Cloud Build

Por repositorio, se configuran:

  • Trigger dev/qa — para certificación
  • Trigger prd — para producción
  • Service Account con permisos de despliegue
  • Variables _DATAOPS_VARIABLES en cada trigger
👥 Responsabilidades

Data / ML Engineer

  • Configura el repositorio
  • Ejecuta y valida el despliegue en dev/qa (Build Id)

Cloud Operator

  • Revisa y valida el Build Id provisto
  • Ejecuta el trigger de producción

del Framework

Arquetipo de proyecto, componentes y sistema de variables

Arquetipo de Proyecto — Estructura del Repositorio

[repositorio]/ ├── deploy/ │ ├── deploy_dev.json ← qué se despliega en dev │ ├── deploy_qa.json │ └── deploy_prd.json ← qué se despliega en prd │ ├── data/bigquery/ ← scripts SQL (sin YAML) │ ├── ddl/ ← CREATE TABLE / VIEW │ │ └── [categoria]/ │ ├── sp/ ← STORED PROCEDURES │ │ └── [categoria]/ │ └── dml/ ← CALL / INSERT (solo dev) │ ├── image/ ← Docker image YAMLs ├── service/ │ ├── cloud_run/ │ ├── cloud_function/ │ ├── vertex/ ← ML Pipelines │ └── pubsub/ └── pipeline/ └── workflow/ ← Cloud Workflows
deploy_[env].json
Lista declarativa de artefactos a desplegar por ambiente.
El framework respeta el orden de ejecución automáticamente.
data/bigquery/
Scripts SQL puros — DDL, SP y DML. No necesitan YAML de configuración. El framework los ejecuta directamente en BigQuery.
service/ y pipeline/
Cada componente tiene su deploy_config.yaml con flags de configuración y variables de entorno (env_vars).

Arquetipo de Componentes — YAML

Todo componente (excepto SQL) se configura mediante un deploy_config.yaml con 2 bloques.

Bloque 1 — Configuración de despliegue
# Flags del componente project: ${env}-itc-customer-services region: us-central1 name: ${env}-mi-servicio service_account: ${env}-sa@${env}-itc-cs.iam... image: us-central1-docker.pkg.dev/... min_instances: 0 max_instances: 3
Bloque 2 — Variables de entorno
env_vars: # 1. Variables de ambiente ENV: ${env} PIPELINE_DISPLAY_NAME: ${env}-proceso # 2. Tablas BigQuery input PROJECT_INPUT: ${project_mi_tabla} DATASET_INPUT: ${dataset_mi_tabla} TABLE_INPUT: ${table_mi_tabla} # 3. Datasets de trabajo PROJECT_OUT: ${project_analytics} DATASET_STAGE: ${dataset_stage} DATASET_OUT: ${dataset_analytics}

Sistema de Variables

Tres tipos de variables disponibles en todos los YAMLs — nunca se hardcodean proyectos, datasets ni tablas.

Sintaxis Origen Cuándo se resuelve
${env} env_[env].json del framework — reemplazo estático por ambiente Antes de cada step
${VARIABLE} _DATAOPS_VARIABLES del trigger Cloud Build — config del proyecto Antes de cada step
${DATAOPS_VARIABLE} dataops_variable_value.txt — outputs de steps anteriores En tiempo de ejecución

Buenas Prácticas — Stored Procedures Parametrizados

Un SP que funciona en dev debe funcionar igual en prd — solo cambiando los parámetros.

✅ Premisas
  • Toda referencia a tabla va parametrizada (proyecto, dataset, nombre)
  • Se construyen queries dinámicos con FORMAT() + EXECUTE IMMEDIATE
  • El SP es portátil entre ambientes sin modificar el código
Orquestación recomendada
  • Cloud Workflows como orquestador principal
  • Ejecución de SPs y servicios vía API (impersonando SA)
  • Manejo de errores y notificaciones Pub/Sub integrado
-- Definición del SP CREATE OR REPLACE PROCEDURE `${project_analytics}.${dataset_sp}.sp_proceso` ( IN p_project_in STRING, IN p_dataset_in STRING, IN p_table_in STRING, IN p_project_out STRING, IN p_dataset_out STRING ) BEGIN DECLARE sql STRING; SET sql = FORMAT(""" INSERT INTO `%s.%s.resultado` SELECT * FROM `%s.%s.%s` WHERE fecha = CURRENT_DATE() """, p_project_out, p_dataset_out, p_project_in, p_dataset_in, p_table_in ); EXECUTE IMMEDIATE sql; END;

Variables en Vertex AI — deploy_config.yaml

Las env_vars del pipeline se organizan en 4 bloques con convenciones estrictas de tipado.

# deploy_config_train.yaml project: ${project_analytics} service_account: ${env}-pipeline-sa@... region: us-central1 bucket: gs://${env}-pipeline-bucket pipelines: - notebook/pipeline-train.ipynb env_vars: # ── 1. Framework ───────────────────── ENV: ${env} PIPELINE_DISPLAY_NAME: ${env}-mi-modelo-train PIPELINE_DESCRIPTION: "Pipeline de entrenamiento" PIPELINE_PATH_ROOT: mi-modelo/train PIPELINE_BUCKET_PROJECT_PATH: gs://bucket/ PIPELINE_BUCKET: gs://${env}-pipeline-bucket # ── 2. Tablas BigQuery input ────────── PROJECT_INPUT: ${project_mi_tabla_input} DATASET_INPUT: ${dataset_mi_tabla_input} TABLE_INPUT: ${table_mi_tabla_input} # ── 3. Paths GCS ───────────────────── MODEL_ARTIFACTS: gs://${env}-bucket/artifacts/ # ── 4. Hiperparámetros y recursos ──── LEARNING_RATE: 0.01 # sin comillas → float() N_ESTIMATORS: 100 # sin comillas → int() MACHINE_TYPE: "n1-standard-4" MACHINE_CPU_LIMIT: "4" # siempre string MACHINE_MEMORY_LIMIT:"15G" # siempre string
Variables auto-inyectadas
No van en env_vars — el framework las inyecta desde los flags top-level:
  • PIPELINE_PROJECT_ID
  • PIPELINE_SERVICE_ACCOUNT
  • PIPELINE_REGION
  • PIPELINE_COMPILE_FILE
Tipado en Python
os.getenv() siempre retorna string.
Numéricos sin comillas en YAML deben castearse:

int(os.getenv("N_ESTIMATORS"))
float(os.getenv("LEARNING_RATE"))
