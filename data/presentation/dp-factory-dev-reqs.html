§1

Contexto y Propósito

El módulo dp_factory_dev es la capa de observabilidad del flujo de fábrica de construcción asistido por IA. Registra la ejecución de cada etapa del ciclo PLAN → RELEASE: qué skill corrió, cuántos tokens consumió, qué artefactos generó, qué hallazgos (findings) detectó y cuánto costó. Funciona de forma análoga al framework de control de procesos productivos, pero aplicado al proceso de construcción en sí.

Motivación

Cuando Claude ejecuta /implement-stage CODING en un repositorio Dataops, genera DDLs, SPs y YAMLs. Sin trazabilidad persistente, no hay forma de responder: ¿cuántas correcciones humanas requirió ese módulo? ¿Cuánto costó en tokens? ¿Qué reglas de compliance fallaron? ¿Qué módulos tienen mayor spec coverage? Este módulo cierra esa brecha.

Alcance

DimensiónDetalle
Tipos de módulo soportadosbq_pipeline, cloud_run_api, vertex_ml, cloud_function
Etapas trazadasPLAN, DISCOVERY, DESIGN, CODING, ORCHESTRATION, MONITORING, DQ, LINEAGE, DATAOPS, COMPLIANCE, TESTING, INFRAOPS, SECURITY, DOCUMENTATION, RELEASE
Granularidad mínimaUna fila en dp_factory_dev_execution por ejecución de etapa (incluyendo re-ejecuciones)
Registro de artefactosUna fila por archivo en dp_factory_dev_artifacts por ejecución
Registro de hallazgosUna fila por issue en dp_factory_dev_findings (compliance violations, alertas de seguridad, observaciones)

Relación con el Ecosistema Existente

El módulo no reemplaza el framework de control de procesos productivos (que monitorea ejecuciones de Cloud Workflows y SPs en producción). Es complementario: el control de procesos monitorea qué corre en producción; dp_factory_dev monitorea cómo se construyó.

§4

Flujo de Registro

Al finalizar cada stage, Claude genera un JSON estructurado como parte del output del comando /implement-stage. Este JSON se envía al endpoint de la metadata API (mismo sistema que monitoring_register) o se escribe a un archivo en deploy/factory_events/ para su procesamiento diferido.

Eventos y Tablas Afectadas

  • project_init
    Disparo: al finalizar el stage PLAN (primer stage de cualquier proyecto).
    INSERT en dp_factory_dev_project (crea la cabecera del proyecto).
    INSERT en dp_factory_dev_execution + dp_factory_dev_artifacts + dp_factory_dev_findings del stage PLAN.
    project execution artifacts findings
  • stage_completed
    Disparo: al finalizar cualquier stage posterior a PLAN con status=completed.
    INSERT en execution + artifacts + findings del stage.
    UPDATE en project: incrementa etapas_completadas, actualiza etapa_actual.
    execution artifacts findings project (UPDATE)
  • stage_failed / stage_retry
    Disparo: cuando un stage termina con status=failed o cuando se re-ejecuta un stage.
    INSERT en execution con stage_attempt_number = N+1 y parent_execution_id = execution_id_anterior. Los artifacts y findings son de la re-ejecución, no del intento fallido.
    execution artifacts findings
  • project_closed
    Disparo: al finalizar el stage RELEASE (último stage del flujo).
    INSERT en execution + artifacts + findings de RELEASE.
    UPDATE en project: status=completed, completed_at, y todos los totales agregados (total_tokens_*, total_loc_generated, total_files_created, total_findings, cost_usd_estimated, compliance_score_pct).
    execution artifacts findings project (UPDATE final)

Fórmula de Costo Estimado

Claude calcula cost_usd_estimated al generar el JSON usando los precios del modelo usado en el stage:

-- claude-sonnet-4-6: $3 / MTok input · $15 / MTok output
cost_usd = (tokens_input_estimated / 1_000_000 × 3.0)
         + (tokens_output_estimated / 1_000_000 × 15.0)

-- claude-opus-4-8: $15 / MTok input · $75 / MTok output
cost_usd = (tokens_input_estimated / 1_000_000 × 15.0)
         + (tokens_output_estimated / 1_000_000 × 75.0)

Reglas de Negocio y Constraints

  • spec_id es UNIQUE en dp_factory_dev_project. Un spec no puede tener dos proyectos activos.
  • Si blocking_issues > 0, el status del execution DEBE ser failed. Claude no puede reportar completed con issues bloqueantes.
  • stage_attempt_number comienza en 1. Cada re-ejecución del mismo stage incrementa el contador. El historial completo de intentos se preserva (no se actualiza, se inserta).
  • compliance_score_pct y validation_bq_rows_checked son NULL en stages que no aplican. No deben forzarse a 0.
  • Si un stage no genera artefactos (ej. COMPLIANCE solo modifica archivos existentes), la lista artifacts puede ser vacía. Si no modifica ningún archivo, files_modified = 0.
  • El campo notes es obligatorio cuando human_corrections > 0 — Claude debe describir qué fue corregido.
  • auto_resolved = true en findings significa que Claude detectó Y solucionó el problema de forma autónoma en el mismo stage, sin loop de feedback humano.

Dashboard de Proyectos Activos

SQL
-- Resumen de proyectos en curso con avance y costo acumulado
SELECT
    p.spec_id,
    p.module_type,
    p.empresa,
    p.autor,
    p.status,
    p.etapa_actual,
    p.etapas_completadas || ' / ' || p.etapas_total AS avance,
    ROUND(
        EXTRACT(EPOCH FROM (NOW() - p.created_at)) / 3600, 1
    ) AS horas_transcurridas,
    COALESCE(SUM(e.cost_usd_estimated), 0)::NUMERIC(10,4) AS costo_acumulado_usd,
    COALESCE(SUM(e.human_corrections), 0) AS correcciones_humanas_total,
    COALESCE(SUM(e.findings_count), 0)    AS findings_total,
    COALESCE(SUM(e.findings_resolved), 0) AS findings_resueltos
FROM dp_factory_dev_project p
LEFT JOIN dp_factory_dev_execution e ON e.project_id = p.project_id
WHERE p.status IN ('in_progress', 'paused')
GROUP BY p.project_id
ORDER BY p.created_at DESC;

SQL
-- Findings abiertos agrupados por severidad, para todos los proyectos activos
SELECT
    p.spec_id,
    p.module_type,
    f.finding_type,
    f.severity,
    f.rule_id,
    f.description,
    e.stage,
    e.completed_at::DATE AS detectado_en
FROM dp_factory_dev_findings f
JOIN dp_factory_dev_execution e ON e.execution_id = f.execution_id
JOIN dp_factory_dev_project p   ON p.project_id = e.project_id
WHERE f.resolved = FALSE
  AND p.status IN ('in_progress', 'paused')
ORDER BY
    CASE f.severity
        WHEN 'critical' THEN 1
        WHEN 'high'     THEN 2
        WHEN 'medium'   THEN 3
        WHEN 'low'      THEN 4
        ELSE 5
    END,
    p.spec_id;

Comparativa de Costo por Tipo de Módulo

SQL
-- Promedio de costo, duración y LOC por tipo de módulo (solo proyectos completados)
SELECT
    p.module_type,
    COUNT(DISTINCT p.project_id)                            AS proyectos,
    ROUND(AVG(p.total_duration_seconds / 3600.0), 1)       AS horas_promedio,
    ROUND(AVG(p.cost_usd_estimated), 4)                     AS costo_usd_promedio,
    ROUND(AVG(p.total_loc_generated))                       AS loc_promedio,
    ROUND(AVG(p.total_files_created))                       AS archivos_promedio,
    ROUND(AVG(p.total_findings))                            AS findings_promedio,
    ROUND(AVG(p.compliance_score_pct), 1)                   AS compliance_score_promedio,
    SUM(p.total_tokens_input + p.total_tokens_output)       AS tokens_total_acumulados
FROM dp_factory_dev_project p
WHERE p.status = 'completed'
GROUP BY p.module_type
ORDER BY costo_usd_promedio DESC;
