§ 01

Contexto y Objetivo

El data-catalog-mcp es un servidor MCP independiente que expone catálogos de datos de múltiples empresas/dominios del grupo Intercorp. Es análogo al knowledge-mcp (que sirve skills, estándares y reglas), pero especializado en navegación estructurada de catálogos de tablas BigQuery.

El servicio lee archivos .md desde el bucket itcm-dp-data-catalog-i9oa (proyecto dev-intercorp-data-storage) y expone herramientas MCP para que agentes IA y analistas puedan descubrir, explorar y leer catálogos de tablas organizados por empresa y dataset.

ℹ

El servicio es solo lectura. La carga de catálogos al bucket la realizan los equipos de cada empresa mediante su propio proceso (script generate_index.py --upload + sync GCS). El MCP no tiene endpoints de escritura.

§ 02

Estructura de Carpetas en GCS

Evaluación de opciones

Estructura
Pros / Contras
Veredicto
{dataset}/{tabla}.md
Sin nivel empresa — colisión garantizada si dos empresas tienen un dataset del mismo nombre (ej. master_party existe en Farmacias y Promart). No escala multi-tenant.
Descartar
{empresa}/{dataset}/catalog_{tabla}.md
El prefijo catalog_ es redundante: el contexto del bucket ya lo implica. Agrega ruido al nombre y complica los lookups por nombre de tabla.
Descartar
{empresa}/{dataset}/{tabla}.md
Espeja la jerarquía BigQuery (proyecto → dataset → tabla). Multi-tenant nativo. Nombre del archivo = nombre de la tabla. Lookup determinista: get_catalog("farmacias","master_party","m_customer") → ruta directa.
Adoptado
✓

Estructura adoptada: {empresa}/{dataset}/{tabla}.md — donde empresa es el slug del negocio (farmacias, promart, oechsle, intercorp, izipay…), no el proyecto GCP.

Árbol de ejemplo en el bucket

itcm-dp-data-catalog-i9oa/ ├── index.json ← índice precomputado (se regenera offline) ├── farmacias/ │ ├── master_party/ │ │ └── m_customer.md │ ├── master_product/ │ │ └── m_promotion.md │ └── bi_itc_attribute_party/ │ └── ba_itc_attr_digital.md ├── promart/ │ └── master_product/ │ ├── m_product.md │ └── m_promotion.md ← mismo nombre de dataset/tabla que farmacias — no colisiona ├── oechsle/ │ └── master_product/ │ └── m_product.md └── intercorp/ └── bi_itc_attribute_party/ ├── ba_itc_attr_digital.md └── ba_itc_attr_education.md

El prefijo raíz del bucket no incluye una carpeta adicional tipo catalog/ — los archivos van directamente bajo {empresa}/…. El índice siempre está en la raíz del bucket.

§ 03

Estructura de archivos .md — Frontmatter

Cada catálogo es un archivo Markdown con bloque YAML frontmatter al inicio. El frontmatter alimenta el index.json y permite búsqueda y filtrado sin leer el cuerpo completo del archivo.

---
empresa:     farmacias
dataset:     master_party
tabla:       m_customer
description: "Tabla maestra de clientes Farmacias con datos de identidad y contacto"
tags:        [party, cliente, maestro, pii]
pii:         true
owner:       data-team-farmacias
updated:     2026-08-18

bigquery:
  project_dev:        dev-intercorp-data-storage
  project_prd:        prd-intercorp-data-storage
  dataset:            master_party
  table:              m_customer
  partition_field:    load_date
  partition_type:     DAY
  clustering_fields:  [iden_party_hash, company_id]
  estimated_rows:     12000000
---

# Cuerpo del catálogo: descripción, diccionario de campos, reglas de negocio, queries de referencia...

Campos obligatorios vs. opcionales

CampoTipoReq.Descripción
empresastringreqSlug del negocio — debe coincidir con la carpeta raíz en GCS
datasetstringreqNombre del dataset BigQuery — debe coincidir con la carpeta
tablastringreqNombre de la tabla — debe coincidir con el nombre del archivo
descriptionstringreqDescripción funcional en lenguaje natural (para search y listados)
tagslist[string]reqPalabras clave para búsqueda semántica
piibooleanreqIndica si la tabla contiene campos PII
ownerstringoptEquipo o persona responsable del catálogo
updateddate YYYY-MM-DDoptÚltima fecha de actualización del catálogo
bigquery.*objectoptMetadata técnica BQ: proyecto, partición, clustering, volumen estimado
§ 04

Herramientas MCP (Tools)

El servidor expone 6 tools. Siguen el mismo patrón que knowledge-mcp: primero leen index.json cacheado (1 call a GCS), y solo si falla iteran el bucket directamente.

list_companies()
Lista todas las empresas/dominios que tienen catálogos disponibles en el bucket. Retorna lista de slugs únicos.
return: list[str] sin parámetros
list_datasets(empresa)
Lista los datasets de una empresa con el conteo de tablas en cada uno.
empresa: str return: list[{dataset, table_count}]
list_tables(empresa, dataset)
Lista las tablas disponibles en un dataset, con descripción corta y flags relevantes (pii, tags).
empresa: str dataset: str return: list[{tabla, description, pii, tags}]
get_catalog(empresa, dataset, tabla)
Retorna el catálogo completo de una tabla — frontmatter más el cuerpo Markdown con diccionario de campos, reglas de negocio y queries de referencia. Es el tool de acceso principal.
empresa: str dataset: str tabla: str return: str (Markdown completo)
get_catalog_summary(empresa, dataset, tabla)
Retorna solo el frontmatter/metadata sin el cuerpo completo. Útil cuando el agente necesita verificar si existe una tabla o conocer sus atributos técnicos sin el costo de traer el catálogo entero.
empresa: str dataset: str tabla: str return: dict (frontmatter parseado)
search_catalog(query, empresa?, dataset?)
Busca catálogos que coincidan con el query (regex o texto literal) en nombre de tabla, descripción, tags y cuerpo del .md. Los filtros empresa y dataset acotan el scope antes de buscar.
query: str empresa?: str (opcional) dataset?: str (opcional) return: list[{empresa, dataset, tabla, description, match_context}]
§ 05

Estructura del index.json

El índice se genera offline con el script tools/generate_index.py --upload y se sube al bucket. Cada tool lo lee en la primera llamada y lo cachea por 5 minutos (TTL igual que knowledge-mcp).

// index.json — raíz del bucket
[
  {
    "path":        "farmacias/master_party/m_customer.md",
    "empresa":     "farmacias",
    "dataset":     "master_party",
    "tabla":       "m_customer",
    "description": "Tabla maestra de clientes Farmacias",
    "tags":        ["party", "cliente", "maestro", "pii"],
    "pii":         true,
    "owner":       "data-team-farmacias",
    "updated":     "2026-08-18",
    "bigquery_ref": "master_party.m_customer"
  },
  // ... una entrada por tabla
]

Búsqueda sobre el índice

La tool search_catalog opera en dos fases sobre el índice:

  • Fase 1 — filtro rápido sobre index.json: aplica regex sobre tabla + description + tags (sin abrir archivos). Retorna candidatos.
  • Fase 2 — full-text sobre cuerpo: solo si la búsqueda no es satisfecha por el índice (query muy específico), descarga y busca en el cuerpo de los candidatos filtrados. Máx. 20 archivos en fase 2.
⚠

Si index.json no existe o está vacío, el servicio hace fallback iterando el bucket directamente — lento pero funcional. Siempre regenerar el índice después de subir catálogos nuevos.

Script offline: generate_index.py

Itera el bucket, lee el frontmatter YAML de cada .md, y construye el array JSON del index.json. Se sube automáticamente al mismo bucket. Debe ejecutarse después de cada batch de catálogos nuevos.

# Uso
python tools/generate_index.py --bucket itcm-dp-data-catalog-i9oa
python tools/generate_index.py --bucket itcm-dp-data-catalog-i9oa --upload    # sube al bucket
python tools/generate_index.py --empresa farmacias --upload               # solo una empresa

ℹ

La separación en dos MCPs independientes es intencional: el knowledge-mcp sirve el know-how del equipo de datos (cómo construir); el datacatalog-mcp sirve el inventario de datos (qué existe). Son contextos distintos con ciclos de actualización y audiencias diferentes.
